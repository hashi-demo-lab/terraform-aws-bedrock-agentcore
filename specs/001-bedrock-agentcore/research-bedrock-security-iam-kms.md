## Research: Security baseline for AWS Bedrock AgentCore Terraform module — least-privilege IAM, KMS, CloudWatch logging, X-Ray, Guardrails

### Decision

Adopt a "secure by default, no opt-out" baseline that hardcodes encryption (customer-managed KMS, BYO via `kms_key_arn`), CloudWatch log group creation with KMS encryption + 90-day retention, X-Ray tracing on the agent (`tracing_configuration` block with `type = "ACTIVE"`), and a least-privilege execution role generated by the module from a narrow template policy scoped to the foundation model ARN, the KMS key ARN, the log group ARN, optionally the action-group Lambda ARNs, and optionally the knowledge base ARN. Bedrock Guardrails are surfaced as an optional but recommended sub-resource (`aws_bedrock_guardrail` + `aws_bedrock_guardrail_version`) wired through the agent's `guardrail_configuration` block with `HIGH` content filter strength on all harm categories by default.

### Resources Identified

- **Primary Resource**: `aws_bedrockagent_agent` — the Bedrock Agent. Key arguments:
  - `agent_name` (required)
  - `agent_resource_role_arn` (required) — the execution role we provision
  - `foundation_model` (required) — e.g. `anthropic.claude-3-5-sonnet-20241022-v2:0`
  - `customer_encryption_key_arn` (optional but **set by default in this module**) — CMK ARN for agent state at rest
  - `instruction` (required)
  - `idle_session_ttl_in_seconds`
  - `prompt_override_configuration` (optional block)
  - `guardrail_configuration` block: `guardrail_identifier` + `guardrail_version`
- **Supporting Resources**:
  - `aws_iam_role` — execution role, trust policy `bedrock.amazonaws.com` with `aws:SourceAccount` + `aws:SourceArn` confused-deputy conditions
  - `aws_iam_role_policy` (inline) — least-privilege policy generated from the template below; inline keeps the policy lifecycle bound to the role
  - `aws_kms_key` — customer-managed CMK (created when `kms_key_arn` is null), with rotation enabled and key policy granting `bedrock.amazonaws.com` and `logs.<region>.amazonaws.com` via `kms:ViaService` conditions
  - `aws_kms_alias` — `alias/bedrock-agent-<name>`
  - `aws_cloudwatch_log_group` — `/aws/bedrock/agents/<agent_name>` (or `<prefix>` from input), `kms_key_id` set to the CMK, `retention_in_days` default 90
  - `aws_bedrockagent_agent_action_group` (optional, `for_each`) — action group, references `lambda_arn` we add to the role policy
  - `aws_bedrockagent_agent_knowledge_base_association` (optional) — KB association, KB ARN added to the role policy
  - `aws_bedrock_guardrail` (optional, default-on toggle `enable_guardrails = true`) — content/topic/word/PII filters
  - `aws_bedrock_guardrail_version` (optional) — immutable published version pinned into the agent
  - `aws_bedrockagent_agent_alias` — stable alias pointing at a prepared agent version (consumers invoke via alias)
- **Key Arguments** (security-critical, always-on):
  - `customer_encryption_key_arn` — module always passes a CMK ARN
  - `guardrail_configuration.guardrail_version` — pinned (never `DRAFT`)
  - `tracing_configuration { type = "ACTIVE" }` — on the agent (or agent alias `routing_configuration`, depending on provider version)
  - On `aws_iam_role`: `assume_role_policy` with `aws:SourceAccount = data.aws_caller_identity.current.account_id` and `aws:SourceArn = arn:aws:bedrock:<region>:<account>:agent/*` (or scoped to the specific agent ARN once created — handled with two-pass policy or wildcard on agent id only)
  - On `aws_cloudwatch_log_group`: `kms_key_id`, `retention_in_days`, `skip_destroy = false`
  - On `aws_kms_key`: `enable_key_rotation = true`, `deletion_window_in_days = 30`
- **Key Outputs**:
  - `agent_id` (`string`)
  - `agent_arn` (`string`)
  - `agent_alias_arn` (`string`) — invoke target for consumers
  - `execution_role_arn` (`string`)
  - `kms_key_arn` (`string`) — whether created or passed in
  - `log_group_name` (`string`), `log_group_arn` (`string`)
  - `guardrail_id` (`string`, conditional), `guardrail_version` (`string`, conditional)
- **Security Considerations**:
  - Encryption: CMK mandatory; module never allows `customer_encryption_key_arn = null` to reach the resource.
  - Logging: log group always created with CMK + retention; no toggle to disable.
  - Tracing: X-Ray tracing on by default; toggle removed (constitutional).
  - IAM: no `Resource = "*"` on `bedrock:InvokeModel` — must be the foundation model ARN; no `lambda:InvokeFunction = "*"` — must be the explicit action-group Lambda ARNs; KMS permissions scoped to the single CMK with `kms:ViaService` conditions.
  - Confused deputy: trust policy uses `aws:SourceAccount` and `aws:SourceArn` per AWS Bedrock cross-service confused-deputy guidance.
  - Guardrails: `enable_guardrails = true` default; content filters at `HIGH` for `SEXUAL`, `VIOLENCE`, `HATE`, `INSULTS`, `MISCONDUCT`, `PROMPT_ATTACK`.

### Rationale

**1. Required IAM permissions for a Bedrock Agent execution role.**
Per *AWS Bedrock User Guide — Service role for Amazon Bedrock Agents* (`docs.aws.amazon.com/bedrock/latest/userguide/agents-permissions.html`), the agent execution role needs:

- Trust relationship: `bedrock.amazonaws.com` with confused-deputy conditions:
  ```json
  {
    "Effect": "Allow",
    "Principal": { "Service": "bedrock.amazonaws.com" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": { "aws:SourceAccount": "<account-id>" },
      "ArnLike":      { "aws:SourceArn": "arn:aws:bedrock:<region>:<account-id>:agent/*" }
    }
  }
  ```
- `bedrock:InvokeModel` on the *foundation model ARN* — `arn:aws:bedrock:<region>::foundation-model/<modelId>` (no account in foundation-model ARNs; this is correct).
- `bedrock:GetAgent`, `bedrock:GetAgentAlias`, `bedrock:InvokeAgent` are caller-side (granted to the *invoker*, not the agent role) — the agent role itself does **not** need `InvokeAgent`. The module's IAM policy therefore omits these from the execution role and only documents them in `examples/complete/` for the consumer principal.
- For action groups using Lambda: `lambda:InvokeFunction` scoped to each action-group Lambda ARN. Per *Action group permissions* (`docs.aws.amazon.com/bedrock/latest/userguide/agents-permissions.html#agents-permissions-action-group`), the resource-based policy on each Lambda must also allow `bedrock.amazonaws.com` to invoke with `aws:SourceArn` set to the agent ARN — surfaced as `aws_lambda_permission` resources in the module per action group.
- For Knowledge Base association: `bedrock:Retrieve` and `bedrock:RetrieveAndGenerate` scoped to the KB ARN `arn:aws:bedrock:<region>:<account-id>:knowledge-base/<kb-id>`. (Note: `RetrieveAndGenerate` also requires `InvokeModel` on whatever model the KB synthesises with — same FM ARN we already grant.)
- For CloudWatch logging: `logs:CreateLogStream`, `logs:PutLogEvents`, `logs:DescribeLogStreams` scoped to the log group ARN `arn:aws:logs:<region>:<account-id>:log-group:/aws/bedrock/agents/<name>:*`.
- For X-Ray tracing (when enabled): `xray:PutTraceSegments` and `xray:PutTelemetryRecords` — `Resource: "*"` is required by the X-Ray service (X-Ray does not support resource-level permissions for these two actions, per *AWS X-Ray IAM* docs `docs.aws.amazon.com/xray/latest/devguide/security_iam_service-with-iam.html`); module documents this and is the *only* `*` in the policy.
- For KMS (using the CMK at rest): `kms:Decrypt`, `kms:GenerateDataKey`, `kms:DescribeKey` scoped to the CMK ARN with a `kms:ViaService` condition for `bedrock.<region>.amazonaws.com`.

**2. KMS key policy required for Bedrock to use a customer-managed CMK.**
Per *Encryption of Bedrock agent resources* (`docs.aws.amazon.com/bedrock/latest/userguide/encryption-agents.html`) and *Permissions for using KMS keys with CloudWatch Logs* (`docs.aws.amazon.com/AmazonCloudWatch/latest/logs/encrypt-log-data-kms.html`), the CMK key policy must:

- Grant the account root `kms:*` (so admins retain control — without this the key becomes unmanageable).
- Grant the CloudWatch Logs service principal — for the log group encryption to work, you grant the *regional logs principal*, not the global one:
  ```json
  {
    "Effect": "Allow",
    "Principal": { "Service": "logs.<region>.amazonaws.com" },
    "Action": [
      "kms:Encrypt*", "kms:Decrypt*", "kms:ReEncrypt*",
      "kms:GenerateDataKey*", "kms:Describe*"
    ],
    "Resource": "*",
    "Condition": {
      "ArnLike": { "kms:EncryptionContext:aws:logs:arn":
        "arn:aws:logs:<region>:<account-id>:log-group:/aws/bedrock/agents/*" }
    }
  }
  ```
- Grant the Bedrock service principal (`bedrock.amazonaws.com`) `kms:Decrypt`, `kms:GenerateDataKey`, `kms:DescribeKey` with a confused-deputy `aws:SourceAccount` condition. AWS Bedrock supports `kms:ViaService` for `bedrock.<region>.amazonaws.com`; the module uses both `aws:SourceAccount` and `kms:ViaService` for defence in depth.
- Grant the agent execution role `kms:Decrypt` + `kms:GenerateDataKey` (the role's identity-policy permissions are necessary but not sufficient — KMS uses a dual control model).

The module enables `enable_key_rotation = true` (CIS AWS 3.8) and sets `deletion_window_in_days = 30` (max 30, gives recovery window). `bypass_policy_lockout_safety_check = false` (default) prevents accidentally locking ourselves out.

**3. CloudWatch log group naming convention.**
AWS Bedrock does not create a log group automatically for agent invocation traces; the consumer (or this module) must create it. The convention used by AWS docs and AWS samples (`docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html`) is:

- Model invocation logs: `/aws/bedrock/modelinvocations`
- Agent runtime logs (from action group Lambdas): `/aws/lambda/<function-name>` (per-Lambda)
- Agent traces (when traces are enabled on `InvokeAgent`): consumer-supplied log group; this module standardises on `/aws/bedrock/agents/<agent_name>` with override variable `log_group_name_override`.

Defaults applied by this module:
- `kms_key_id` = the CMK ARN (always, no opt-out).
- `retention_in_days` = `90` (configurable via `log_retention_days`, validated to one of `[1, 3, 5, 7, 14, 30, 60, 90, 120, 150, 180, 365, 400, 545, 731, 1827, 3653]` per CloudWatch Logs API).
- `skip_destroy = false` so destroy operations are explicit.
- AWS Well-Architected Reliability Pillar OPS 8 and CIS AWS Benchmark 3.4 (CloudTrail logs encrypted with CMK) — applied by analogy to application logs.

**4. X-Ray tracing for Bedrock agents.**
Per *Monitoring Bedrock Agents* (`docs.aws.amazon.com/bedrock/latest/userguide/agents-monitor.html`), tracing for Bedrock agents has two layers:

- **Agent invocation trace** (a runtime payload returned by the `InvokeAgent` API when `enableTrace=true`) — controlled at *invocation time* by the caller, not by the agent resource. The Terraform resource has no flag for this; the module documents that consumers should call with `enableTrace=true` in non-prod and route to CloudWatch.
- **AWS X-Ray distributed tracing** — supported via the action-group Lambda functions and any downstream services. To get end-to-end X-Ray spans, the agent execution role needs `xray:PutTraceSegments` + `xray:PutTelemetryRecords`, and each action-group Lambda must have `tracing_config { mode = "Active" }`.

The Terraform `aws_bedrockagent_agent` resource (provider `hashicorp/aws` >= 5.50) does **not** expose a `tracing_configuration` block as of the latest schema — tracing is implicit through IAM. Therefore the module:
- Adds `xray:PutTraceSegments` + `xray:PutTelemetryRecords` (Resource `*` — required by X-Ray) to the execution role unconditionally.
- For each `aws_lambda_function` it provisions for an action group, sets `tracing_config { mode = "Active" }`.
- Documents the `enableTrace=true` invocation-time recommendation in the module README.

**5. Bedrock Guardrails.**
Resources from `hashicorp/aws` provider:

- `aws_bedrock_guardrail` — top-level guardrail. Key arguments:
  - `name`, `blocked_input_messaging`, `blocked_outputs_messaging`
  - `content_policy_config { filters_config { type, input_strength, output_strength } }` — per AWS docs, types are `SEXUAL`, `VIOLENCE`, `HATE`, `INSULTS`, `MISCONDUCT`, `PROMPT_ATTACK`. Strengths are `NONE`, `LOW`, `MEDIUM`, `HIGH`. Module default: **all six at `HIGH`** for both input and output (PROMPT_ATTACK has no `output_strength` — input only).
  - `sensitive_information_policy_config { pii_entities_config }` — enables PII detection/anonymisation. Default action: `BLOCK` for `EMAIL`, `PHONE`, `US_SOCIAL_SECURITY_NUMBER`, `CREDIT_DEBIT_CARD_NUMBER`; `ANONYMIZE` for others.
  - `topic_policy_config` (optional, consumer-supplied)
  - `word_policy_config` (optional, consumer-supplied + AWS-managed `PROFANITY` list on)
  - `kms_key_arn` — encryption for the guardrail config; module sets to same CMK.
- `aws_bedrock_guardrail_version` — publishes an immutable version. Required because the agent's `guardrail_configuration` must reference a *numbered version* (`"1"`, `"2"`, …); referencing `"DRAFT"` is allowed by the API but considered insecure (mutable) and the module forbids it.

Wiring on the agent:
```hcl
resource "aws_bedrockagent_agent" "this" {
  # ...
  dynamic "guardrail_configuration" {
    for_each = var.enable_guardrails ? [1] : []
    content {
      guardrail_identifier = aws_bedrock_guardrail.this[0].guardrail_id
      guardrail_version    = aws_bedrock_guardrail_version.this[0].version
    }
  }
}
```

**6. CIS / NIST baselines applicable to Bedrock workloads.**
There is no Bedrock-specific CIS Benchmark yet (as of v3.0.0 of CIS AWS Foundations). The module maps to the closest applicable controls:

| Control                                                              | Applied here                                                  |
| -------------------------------------------------------------------- | ------------------------------------------------------------- |
| CIS AWS 1.16 — IAM policies attached only to groups/roles, not users | Module emits role-attached policies only; no user attachments |
| CIS AWS 1.22 — No `*:*` policies                                     | Inline policy is fully scoped (X-Ray `*` documented)          |
| CIS AWS 3.4 — CloudTrail logs encrypted with CMK                     | Applied by analogy: agent log group encrypted with CMK        |
| CIS AWS 3.6 — S3 bucket access logging on CloudTrail bucket          | N/A (no S3 in this module)                                    |
| CIS AWS 3.8 — KMS rotation enabled                                   | `enable_key_rotation = true` hardcoded                        |
| CIS AWS 3.9 — VPC Flow Logs                                          | N/A                                                           |
| NIST 800-53 AC-6 (Least Privilege)                                   | Inline policy scoped to specific ARNs                         |
| NIST 800-53 SC-12, SC-13 (Cryptographic key establishment / use)    | CMK with rotation                                             |
| NIST 800-53 SC-28 (Protection of information at rest)                | CMK at rest enforced                                          |
| NIST 800-53 AU-2, AU-9 (Audit events / Protection of audit info)     | CloudWatch log group with CMK                                 |
| NIST AI RMF MAP-2.3, MEASURE-2.6 (content safety)                    | Bedrock Guardrails default-on                                 |
| AWS Well-Architected SEC03-BP02 (least-privilege roles)              | Inline policy is the default                                  |
| AWS Well-Architected SEC08-BP02 (encrypt at rest)                    | CMK enforced                                                  |
| AWS Well-Architected SEC04-BP01 (centralised logging)                | Log group + retention + CMK                                   |

**7. Trivy / tflint rules that commonly fire on Bedrock + IAM + KMS — and how the module avoids them.**

| Rule                                                              | Avoidance                                                                                       |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `AVD-AWS-0057` (no IAM `*:*` policies)                            | Inline policy scoped to specific ARNs; X-Ray `*` is the only wildcard and is justified inline   |
| `AVD-AWS-0342` (KMS key rotation must be enabled)                 | `enable_key_rotation = true` hardcoded                                                          |
| `AVD-AWS-0017` (CloudWatch log groups should be encrypted by CMK) | `kms_key_id` is always set                                                                      |
| `AVD-AWS-0017`/`CKV_AWS_158` (log group encryption)               | Same — CMK mandatory                                                                            |
| `CKV_AWS_338` (CloudWatch log group retention >= 1 year)          | Default 90 — module exposes `log_retention_days` and recommends 365 in production examples      |
| `CKV_AWS_111` (no `iam:Passrole` to `*`)                          | Module never grants `iam:PassRole`                                                              |
| `CKV_AWS_109` (IAM policy with no constraints)                    | All KMS, Lambda, Bedrock actions are resource-scoped                                            |
| `CKV2_AWS_67` (KMS key rotated)                                   | `enable_key_rotation = true`                                                                    |
| `tflint aws_iam_policy_document_gov_friendly_arns`                | All ARNs use `data.aws_partition.current.partition` for GovCloud/China compatibility            |
| `tflint terraform_required_providers`                             | `versions.tf` declares `aws ~> 5.50` (or `>= 5.50`) and `random ~> 3.6`                          |
| `AVD-AWS-0338` (Lambda tracing should be Active)                  | All action-group Lambdas created by module set `tracing_config { mode = "Active" }`             |
| `CKV_AWS_50` (Lambda X-Ray tracing enabled)                       | Same as above                                                                                   |
| `CKV_AWS_115`/`CKV_AWS_116` (Lambda concurrency / DLQ)            | Module sets reserved concurrency = 0 (off, but configurable) and DLQ via SQS optional variable |

### Concrete least-privilege execution-role policy (template emitted by the module)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "InvokeFoundationModel",
      "Effect": "Allow",
      "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
      "Resource": "arn:${partition}:bedrock:${region}::foundation-model/${foundation_model_id}"
    },
    {
      "Sid": "WriteAgentLogs",
      "Effect": "Allow",
      "Action": ["logs:CreateLogStream", "logs:PutLogEvents", "logs:DescribeLogStreams"],
      "Resource": "${log_group_arn}:*"
    },
    {
      "Sid": "UseCMK",
      "Effect": "Allow",
      "Action": ["kms:Decrypt", "kms:GenerateDataKey", "kms:DescribeKey"],
      "Resource": "${kms_key_arn}",
      "Condition": {
        "StringEquals": {
          "kms:ViaService": [
            "bedrock.${region}.amazonaws.com",
            "logs.${region}.amazonaws.com"
          ]
        }
      }
    },
    {
      "Sid": "XRayTracing",
      "Effect": "Allow",
      "Action": ["xray:PutTraceSegments", "xray:PutTelemetryRecords"],
      "Resource": "*"
    },
    {
      "Sid": "InvokeActionGroupLambdas",
      "Effect": "Allow",
      "Action": ["lambda:InvokeFunction"],
      "Resource": ${jsonencode(action_group_lambda_arns)},
      "Condition": { "StringEquals": { "AWS:SourceAccount": "${account_id}" } }
    },
    {
      "Sid": "RetrieveFromKnowledgeBase",
      "Effect": "Allow",
      "Action": ["bedrock:Retrieve", "bedrock:RetrieveAndGenerate"],
      "Resource": ${jsonencode(knowledge_base_arns)}
    },
    {
      "Sid": "ApplyGuardrail",
      "Effect": "Allow",
      "Action": ["bedrock:ApplyGuardrail"],
      "Resource": "${guardrail_arn}"
    }
  ]
}
```

The last three statements are emitted only when the corresponding feature is enabled (`for_each` on action groups, `count` on KB association, `count` on guardrails). Trivy `AVD-AWS-0057` will not fire because there are no `*` actions or `*` resources except the documented X-Ray statement, which is unavoidable per AWS X-Ray docs.

### Alternatives Considered

| Alternative                                                   | Why Not                                                                                                                                                            |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| AWS-managed policies (e.g. `AmazonBedrockFullAccess`)         | Grants `bedrock:*` on all resources — violates least privilege and CIS AWS 1.22                                                                                    |
| AWS-owned encryption (no CMK)                                 | Cannot satisfy "secure by default with no way to disable encryption" requirement and prevents audit/key rotation control; AWS-owned keys are not customer-visible  |
| Aliased KMS principal `kms.<region>.amazonaws.com`            | Not a real service; `kms:ViaService` must reference the service that calls KMS (`bedrock.<region>.amazonaws.com`)                                                  |
| Logging via Kinesis Firehose to S3                            | More moving parts; CloudWatch Logs is the canonical path for agent traces and supports CMK natively                                                                |
| `tracing_configuration` block on `aws_bedrockagent_agent`     | Not present in current provider schema; tracing is granted via IAM and Lambda `tracing_config`. Revisit when provider exposes a tracing block                      |
| Agent referencing Guardrail `DRAFT` version                   | DRAFT is mutable; pinning a numbered version with `aws_bedrock_guardrail_version` provides immutability and rollback — required for production safety              |
| Wildcard `bedrock:InvokeModel` on `Resource: "*"`             | Lets the role invoke *any* model, including expensive or unapproved ones; scope to the configured FM ARN only                                                      |
| Granting `lambda:InvokeFunction` on `*`                       | A common Trivy `AVD-AWS-0057` finding; module always scopes to the explicit action-group Lambda ARNs                                                              |
| Putting CloudWatch Logs principal in trust policy of CMK      | Trust policies are for STS:AssumeRole; CW Logs uses the *key policy*, not a trust policy                                                                           |
| Skipping confused-deputy conditions (`aws:SourceAccount`)     | AWS explicitly calls this out as the cross-service confused-deputy pattern; omitting would be flagged by tfsec/Trivy `AVD-AWS-0345`                                |
